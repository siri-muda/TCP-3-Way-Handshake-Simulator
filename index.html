Handshake Process at a Glance

RFC 793 Protocol Model
Step 1 Client → Server

SYN (Synchronize)

Client picks random Initial Sequence Number (e.g. ISN=1000). Informs server of its intent to connect.

State: CLOSED → SYN-SENT
Step 2 Server → Client

SYN-ACK

Server acknowledges client's SYN (Ack = 1001) and sends its own sequence number (ISN=5000).

State: LISTEN → SYN-RECEIVED
Step 3 Client → Server

ACK (Acknowledge)

Client acknowledges server's SYN (Ack = 5001). Virtual circuit is established on both ends!

State: ESTABLISHED (Both)

Why Does TCP Require Exactly a 3-Way Handshake?

Top Viva Examination Question

Why Not a 2-Way Handshake?

In an unreliable IP network, packets can be delayed by intermediate routers. If a client transmits a SYN that gets delayed, times out, and later arrives at the server, a 2-way protocol would force the server to allocate memory and open a connection immediately upon sending SYN-ACK. However, the client already discarded that attempt! This creates a dangerous half-open ghost connection where the server wastes memory waiting for data that will never arrive.

Why Not a 4-Way Handshake?

A 4-way exchange (SYN → ACK → SYN → ACK) would be redundant. Because the server needs to acknowledge the client's SYN and also initiate its own sequence synchronization, TCP intelligently piggybacks both operations into a single combined packet: SYN-ACK. This combines steps 2 and 3 into one round-trip transmission, saving network latency while maintaining full mathematical reliability.
